# Myco Milestone 1 — architecture and decision records

Status: proposed, 2026-11-18. Sources: docs/research/eval-frameworks.md,
docs/research/adapters.md, docs/env/windows.md. Spec: docs/product/vision.md.

Consequential decisions are flagged **[CONSEQUENTIAL]** and reported to the outer loop.

## The smallest rigorous slice

Task family: `calc-record-edit` — LibreOffice Calc record edits on Windows 11 ARM64.

- **Fixture.** A `.xlsx` table of records: an `id` key column plus 3–6 data columns
  (text, integer, date, currency). Generated programmatically per trial from a seed, so
  no two trials share a sheet. Sizes vary 5–200 rows.
- **Intent.** `TaskIntent = { fixtureSeed, rowKey, column, newValue }`: "set the cell at
  record `rowKey`, column `column`, to `newValue`, and save the file."
- **Program.** Open the fixture copy in Calc; locate the record row and column header
  through the UI; set the cell; save through the app; close the document.
- **Verification.** Two independent checks, both read-only:
  1. *Edit landed* — UNO readback of the live document (`getValue`/`getString`/`getError`).
  2. *Edit persisted* — close the document, then a host-side parse of the persisted
     `.xlsx` file. `XModifiable.isModified()` is the cheap pre-check that catches a
     missed save before paying for the close/reopen.
  Neither check consults the runner's claims. Expected values are computed host-side
  from `fixtureSeed` + intent parameters (OSWorld's `employee_age_reference` discipline).
- **Definition of done per acceptance row** is in §10.

## ADR-0001 — Two-process split: TypeScript host runtime, Python guest agent [CONSEQUENTIAL]

**Decision.** The core runtime (state model, program runner, verifier orchestration,
evidence, eval harness) is TypeScript on Node 24, developed and unit-tested on macOS
against a fake-app test double. The Windows side is `myco-agent`, a small Python process
in the guest's interactive session, exposing UIA/UNO/screenshot/file ops over
newline-delimited JSON on a loopback port with token auth (see docs/env/windows.md
§Control plane design, which this ADR ratifies).

**Why.** The Windows-side libraries that matter (uiautomation, pywinauto, comtypes,
pyuno) are Python. The host-side ecosystem for harnesses, schemas, and the eventual
MCP-facing product surface is TypeScript. A loopback NDJSON protocol is the boring
boundary between them: versioned, replayable, and trivially mockable — the fake-app test
double speaks the same protocol, so CI exercises the real runner against a fake
transport without Windows.

**Rejected.** All-Python (drags the harness and future product surface into a second
ecosystem for no M1 benefit). All-TypeScript with agent-desktop as the Windows process
(rejected in ADR-0003). Rust (right long-term, wrong for a 6-week milestone).

**Cost.** Two languages in the repo. Mitigated by keeping the guest agent deliberately
thin: no policy, no retries, no verdicts — only ops. All decisions live host-side.

## ADR-0002 — Verification is independent, read-only, and three-valued

**Decision.** The verifier is a separate component (and on Windows, a separate process)
that reads only persisted or object-model state, never the adapter's or runner's claims.
Verdicts are `verified | refuted | uncertain`. `uncertain` covers "could not look":
UNO unreachable, file unreadable, timeout. It is never collapsed into `refuted` and
never counted as success or as a detected failure.

**Why.** OSWorld collapses missing files to score 0; OpenComputer collapses verifier
errors to `passed: False` (docs/research/eval-frameworks.md §4). Collapsing makes "0
false successes" unauditable, because "we proved it failed" and "we could not look"
become indistinguishable. UNO is the only channel that can read Calc cell state
reliably — LibreOffice has no native UIA, only a lossy MSAA→UIA proxy
(docs/research/adapters.md §1, tdf#160982).

**Consequences.** Verifiers are pure functions over `(PersistedState, TaskIntent)`.
Predicates come from a closed declarative language — no `eval()` of task-supplied
strings (OpenComputer's `eval(check["eval"])` is a remote-code hole we do not import).

## ADR-0003 — Adapter: uiautomation actuator + comtypes timeouts; steal agent-desktop's primitives, don't depend on it [CONSEQUENTIAL]

**Decision.** The Windows actuator is built on `uiautomation` (yinkaisheng) with a raw
`comtypes` `IUIAutomation2.SetConnectionTimeout`/`SetTransactionTimeout` call written
alongside it (neither Python library exposes the setters; a hung app must never block
the adapter unboundedly — the "killed app" corruption trial hits exactly this).
Observation uses UFO's query shape: one `FindAllBuildCache` with a composed condition
and a 3-property cache request, hard element cap.

From agent-desktop we adopt the *shapes*, reimplemented in Myco's vocabulary:
- Opaque refs valid only for the `stateVersion` they came from; acting on one throws
  `StaleRefError`; ambiguous matches throw `AmbiguousTargetError`.
- Three-way action outcome: `delivered_verified | delivered_unverified | failed` —
  never a bare "ok".

**Rejected as dependencies.** agent-desktop (no COM/UNO channel, `publish = false`,
zero LibreOffice coverage — right product, wrong first dependency), pywinauto (0.6.9
old, `uia` backend less-travelled), UFO (verification is an LLM judging screenshots —
imports the failure mode M1 exists to fix), Cua (perception extension AGPL).

**Escape hatch.** If the ARM64 re-check (backlog M1-008) fails on the real VM, fall back
to agent-desktop's CI-tested `aarch64-pc-windows-msvc` FFI artifact for UIA and keep
UNO for verification.

## ADR-0004 — Guarded action programs are data, not code

**Decision.** A program is a JSON-serializable sequence of steps:
`{ action, preconditions[], postconditions[] }`. Actions are a closed union
(`click(ref) | typeText(ref, text) | setValue(ref, value) | keyPress(keys) |
waitFor(predicate, timeout)`). Predicates are drawn from a closed declarative language
over the typed state model. The runner observes state before and after every step,
evaluates guards, and aborts on failure with a structured `GuardFailure`. The runner
never decides task success.

**Why.** Programs must be replayable, diffable, and eventually compiled into the
workflow registry (post-M1). Data makes all three trivial; embedded code makes none of
them possible. Per-step guards are what stop errors from compounding silently — the
core thesis.

## ADR-0005 — Failure injection is pluggable, and ground truth is computed outside the guest

**Decision.** Corruptions implement a `FaultInjector` interface:
`{ name, arm(trial), assertExpectation(groundTruth) }`. M1 ships four: `kill-app`
(SIGKILL Calc mid-program), `invalid-target` (intent references a nonexistent row/column
or a stale ref), `delayed-save` (block or defer the save), `focus-change` (steal focus
mid-typing). The eval harness computes ground truth from the fault schedule and intent
parameters on the host, never from guest state.

**Why.** "0 false successes" is only meaningful against independently known ground
truth. OpenAdapt's published numbers (54/72 bad saves reported as saved from the
on-screen "Saved" message; 30/30 from a computer-use agent) are the bar: our
corrupted-trial suite reproduces that failure shape for Calc and must beat it with UNO
read-back (docs/research/eval-frameworks.md §2, §Recommendations 8).

## ADR-0006 — Recovery semantics: known-good versions, retry from snapshot, uncertainty over guessing

**Decision.** Every observed state carries a monotonically increasing `stateVersion`.
The runner records the last version whose postconditions all held as the **known-good
point**. On `GuardFailure` or adapter error, recovery is, in order:
1. Re-observe. If the intent is already satisfied, continue (idempotent resume).
2. Retry the failed step from the known-good point, up to a bounded count.
3. If the app died, relaunch it via the guest agent and resume from the known-good
   point when the operation is reversible; when it is not resumable, abort with
   `uncertain` and the full trace.

**Non-negotiable:** recovery never reports success without a post-recovery verification
pass. An unrecoverable or ambiguous state is reported as `uncertain`, never guessed.

## ADR-0007 — Evidence is machine-readable, per-step, and ledger-shaped

**Decision.** Every run emits `runs/<runId>/trace.jsonl` (one event per observation,
action, guard evaluation, fault injection, recovery) and `runs/<runId>/result.json`
(RunRecord: intent, params, steps with pre/postcondition results and state versions,
guardFailure?, verdict with per-check weighted partial scores, unresolvedState?). The
eval report additionally emits a **conformance ledger**: one row per
(trial, corruption-class, action-kind) with an explicit oracle and an explicit refusal
code, and a `gap` state that is never counted as a pass (Cua's action-support ledger
format). `success_rate` and `check_pass_rate` are reported separately.

## ADR-0008 — Eval harness: parameterized family, false-success accounting against host-side ground truth

**Decision.** The harness takes the task family's parameter generator, runs N trials
per configuration, applies fault injectors on schedule, and emits
`{ trials, succeeded, verified, refuted, uncertain, falseSuccesses, recovered }`.
A false success is `verdict = verified` when host-side ground truth says the intent is
not satisfied. The same harness runs both the Myco path and the screenshot baseline, so
conditions are identical by construction.

## ADR-0009 — Baseline: Agent S3 + UI-TARS-1.5-7B, identical conditions

**Decision.** The screenshot baseline is Agent S3 with UI-TARS-1.5-7B as the grounding
model, run against the same VM, fixtures, intent parameters, and trial schedule as the
Myco path. Cheap general-purpose VLMs are disqualified by measurement (2/16 cell
grounding hits, docs/research/eval-frameworks.md §3.8). If UI-TARS cannot run locally,
its hosting is escalated to the outer loop (potential account/cost).

## ADR-0010 — Environment and reset: ratify docs/env/windows.md

**Decision.** The Windows environment design in docs/env/windows.md is ratified:
UTM Win11 ARM64, SSH transport (never a GUI execution surface), logon-started
`myco-agent` bootstrapped by an `InteractiveToken` scheduled task, reset via
`utmctl start --disposable` if provisioning step P7 validates it, else
`stop --request` → `snapshot restore clean-base` → `start`. LibreOffice pinned to
26.8.3 ARM64 MSI, SHA-256 recorded in-repo (backlog M1-018).

## 10. Definition of done, per acceptance row

| Acceptance row | Exact, checkable definition |
|---|---|
| Real desktop execution | `calc-record-edit` runs against real LibreOffice Calc 26.8.3 on the Win11 ARM64 VM, driven through UIA by `myco-agent`; 30 trials vary row, column, value, and fixture size. |
| Independent verification | Every verdict derives only from UNO readback + host-side parse of the persisted file. Harness test: a run whose adapter reports success while the file lacks the edit yields `refuted` or `uncertain`, never `verified`. |
| Reliability ≥ 27/30 | Eval report over 30 varied normal trials: `verified ≥ 27`. |
| Failure detection | ≥ 10 corrupted trials spanning ≥ 4 corruption classes; `falseSuccesses = 0` in the eval summary. |
| Recovery | One trial class kills Calc mid-program (must relaunch and complete with a post-recovery verification, or end `uncertain`); one class targets an invalid UI element (must raise `GuardFailure`/`StaleRefError` and abort or replan, never false-succeed). Both audited in the ledger. |
| Evidence | Every run directory contains schema-valid `trace.jsonl` and `result.json`; the eval emits the conformance ledger. |
| Baseline | Agent S3 + UI-TARS-1.5-7B runs the same 30 trials on the same VM and fixtures; the report compares `verified` rates side by side. |
| Reproducibility | A runbook (`docs/eval-runbook.md`) lets a fresh agent go from `clean-base` snapshot to full eval report with pinned versions and the MSI SHA-256; demonstrated by an independent reproduction. |
