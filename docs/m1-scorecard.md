## Open a trial in the viewer

Every trial row below links to its own directory under
`docs/research/experiments/m1-runs/`, and each carries the two files the viewer
reads: `result.json` (verdict, evidence) and `trace.jsonl` (timeline).

The **Viewer** column is a deep link that names that row's run by its own `runId`
(the fragment is `#?run=<runId>`, read from the row's `result.json`). Open the run
directory from the column beside it, and the viewer selects that run; the id in the
link is what makes the selection land on the right trace. The viewer is a static
single-file app and cannot read a folder by itself, so the link carries the
selection, not the bytes.

```sh
# One line: build the single-file viewer and open one trial's run.
pnpm --filter viewer build && open "viewer/dist/myco-viewer.html"   # then drop docs/research/experiments/m1-runs/m1-013/trial-0 on it
```

Both scripts hold the table to the artifacts:

```sh
python3 scripts/check-scorecard-links.py        # every link resolves, and every
                                                # fragment matches its result.json runId
python3 scripts/scorecard-viewer-links.py       # rewrite the table; --check verifies
```

The viewer is a static single-file app — it reads the run **in the browser**, so
there is no server to start and no `myco view <run>` CLI (that is designed in
`docs/design/gui-spec.md` but **not implemented**; do not quote it as if it were).
Open the built file, then drag a `trial-<n>` directory onto it. The URL carries
`#?run=<runId>` — the run's own id from its `result.json`, **not** the folder name
(`viewer/src/store.ts` keys a run by `result.json`'s `runId` once the result parses,
so `#?run=trial-0` selects nothing). A selection made before the folder is opened is
pending, and applies when the run with that id arrives.

**Screenshots are deliberately not committed.** A `/tmp` run directory is ~8 MB of
per-step PNGs; `result.json` + `trace.jsonl` is ~8 KB, and the viewer renders the
verdict, evidence and timeline from those two alone. All 54 trials cost 504 KB.

**Verified:** `scripts/check-scorecard-links.py` asserts every link resolves, carries
both files, and that each row's viewer fragment matches that row's `result.json`
`runId` — every row must carry one. `scripts/scorecard-viewer-links.py --check` holds
the table to the generated form. Run both after editing the table:

```sh
python3 scripts/check-scorecard-links.py
```

## Reproducibility test plan (row 8)

can actually reproduce the evaluation from the repo, so the test is behavioural, not editorial.

**Protocol.** One agent who has never touched this project, given only the repo and the VM
bundle, attempts the runbook end to end, and writes down every point where the repo is
insufficient.

|---|---|
| 1. Read only the repo | The operator reaches a runnable command sequence without asking a question that the repo could have answered |
| 2. Preconditions (§1) | Obtains the VM bundle, `ssh_config` + `id_ed25519`, host scripts, GUI-session permission — and **nothing else is needed** |
| 3. Reset (§3) → deploy (§4) → desktop proof (§5) | Each step's stated expected output is observed |

## Decision: arm-002 is not the baseline (2026-11-23)

**Option B.** Arm-002 completed as a **recorded run** and is **not scored** against
criterion 7. Its artifacts and analysis are kept at
`docs/research/experiments/c1-arm-002/`.

**Why.** The two arms were not told the same thing:

| | Myco's arm | arm-002 |
|---|---|---|
| Task text | "set the cell at record X, column Y, to Z, **and save the file**" | "Set the Y cell for record X to Z." — no save |
| System prompt | — | "Save and close it" (`PROMPT` in `src/baseline/planner.ts`) |

Measured consequence, re-derived from `accounting.json`: **0 `press_key` calls
across 422 actions** (`click` 398, `type_text` 24), and `modified` was 16 of 29
refutations. **Only 1 of those 16 typed the expected value** — the other 15 typed a
cell reference such as `'A24\n'`, mostly into the Name Box at `(70,146)` and otherwise
at `(75,146)`, `(70,147)` or `(60,146)`. Index 6 is the one row that typed the expected value,
at `(282,277)`. All 16 terminated on
`planner-no-action` with empty `claims`, so none declared success.

So the save gap is real — no trial ever attempted Ctrl+S — but the transcript does
**not** support "typed the right value and stopped"; for 15 of 16 the right value
was never entered. The instruction difference is still the defect: the baseline was
never told to persist, while Myco's program saves as an explicit step.

**The fix, already merged into the code path.** `src/tasks/task-text.ts` renders the
canonical sentence, imports nothing, and is what `c1-trial.ts` now uses; the
rendered `instruction` is recorded on every row, so future parity is a field diff
rather than a source-reading exercise. A mutation-verified test
(`test/baseline/task-text.test.ts`) fails if the save requirement is dropped.

## Second reason arm-002 is superseded: the 256-token truncation defect (#340)

**Ruled 2026-11-23 by the outer loop.** Two independent reasons the arm-002 numbers
are not a comparison; either alone would disqualify them.

**The defect.** Every C1 model call was capped at `MAX_OUTPUT = 256`, and
`stop_reason` was inspected only for `"refusal"`. A reply cut off mid-tool-call
therefore became partial JSON, the planner found no parseable decision, and
`planner-no-action` was scored **against the agent** — a harness fault recorded as
an agent failure.

**Measured, not inferred.** Across the committed arm-002 rows (444 calls, 29 rows)
the largest **non-truncated** completion is **250 tokens** (row 26), and **22 calls
across 22 distinct rows landed on exactly 256** — the ceiling, not the model's
answer.

**What that does and does not establish.** It establishes that **arm-002 ran under
the defective configuration**, so its numbers are not directly comparable to a run
without it. It does **not** establish that truncation caused arm-002's results, and
this document must not be read that way:

- **Almost every 256-hit has a real trajectory** — rows with 3, 7, 14, 20 and 28
  steps. A truncated *final* call after 28 successful actions is not what produced
  that row's verdict.
- **Rows 5 and 13 have the truncation signature** (1 step, final completion at the
  ceiling: `[153, 256]` and `[221, 256]`), and **rows 3 and 29 have the zero-step shape**
  (no step, one completion `[256]`), the shape that stopped arm-003d r2 at trials 3 and 4.
- `FINAL.md` attributes arm-002's **zero-action `modified` rows to the model typing
  cell references into the Name Box**, which is an independent explanation and
  remains the recorded one for those rows.

**Consequence.** arm-002's headline figures — 29 refuted, `modified` 16 of 29 — are
counts from a run **on a defective configuration**, so they cannot be compared
against a run without it. **arm-002 must not be re-run**: it is recorded as
superseded, not re-measured.

**The canonical C1 baseline is arm-003d, run with the fix (#340).** Its run **r6** is the one
row 7 compares with Myco's arm (`docs/research/experiments/c1-arm-003/r6/`). **Instruction parity still applies** — the shared
task text above is a separate requirement, unaffected by this ruling.

**Fix and evidence:** PR #340 (`fix(TIF-164): a truncated reply is a harness fault,
not an agent failure`) raises the ceiling to 1024 with ~4x headroom over the largest
observed completion, throws `PlannerFailure` on `stop_reason: "max_tokens"` so the
trial is **omitted** rather than scored, and wires the two-consecutive-failure abort
to scored rows.

**Arm-003** (completed as run r6 on 2026-11-24, 30/30 scored; see row 7) re-ran 30 trials with the shared text,
the same Sonnet planner, the same snapshot, and a **$9.00 cap on total committed
spend**, read from `report.json.c1ChargedMicros`: arm-002 booked $1.555362, and the spike trial's committed
spend is $0.076808 (`docs/research/experiments/c1-arm-001/spike-trial-0.json`). From the uncommitted booking
ledger, unverifiable: the spike booked $0.076800, for **$1.632162** at arm-002's close. Design:
`docs/research/experiments/c1-arm-003-design.md`.

### The C1 baseline's characteristic failure mode: the save dialog

**Diagnosed 2026-11-24 in `c1-arm-003d/SAVE-DIALOG-LOOP.md` (#381), on r6's first 9 scored rows**
(the lead's ruling in #382 concerned the abort key, not this verdict). Across all 30 rows, 27 of the
29 step-budget failures show the pattern; rows 13 and 21 do not (row 7). The baseline agent's
dominant failure is **not** failing to find or edit the cell — it is failing to
**commit the save**, because saving an `.xlsx` opens LibreOffice's "Keep Current
Format" dialog and the agent presses **`Escape`**, which dismisses the dialog *and
cancels the save*.

The evidence is that the edit succeeds:

| | |
|---|---|
| rows that typed the **correct value** into the **correct cell** | **9 of 9** |
| rows that attempted a save | **9 of 9** |
| rows that completed a save | **0 of 9** |
| `Ctrl+S` presses immediately followed by `Escape` | **61 of 76 (80%)** |

Row 9 is the pure case — `click → Ctrl+S → Escape` repeated nine times with nothing
else. Diagnosis and measurements:
`docs/research/experiments/c1-arm-003d/SAVE-DIALOG-LOOP.md`.

**This is what the row-7 comparison is meant to show**, and it is a finding about the
baseline, not a defect in the harness: the harness requests a fresh frame on every
step (`get_window_state` with `include_screenshot`, no caching) and the edit lands in
9/9 rows, so observation and coordinates work. It matches the r3 modal-loop ruling.

**Consequence for the rule set.** Because every row fails the same diagnosed way, the
two-consecutive-identical-failures abort — which exists to catch a *harness* fault —
would stop the arm at the second row and the comparison would never complete. The
fix is an explicit, recorded acceptance rather than weakening the rule: accepted
causes break the run of failures, anything unaccepted still aborts at 2, and the
acceptance appears in **both** the report and the run identity so a reader can tell an
arm that ran under one from an arm that never needed it. r6's resume command, which
must be repeated in full on every attempt:

```bash
MYCO_PRIOR_SPEND_MICROS=4480732 MYCO_ARM_LIMIT_MICROS=4519268 \
  bash scripts/c1-baseline.sh ~/Projects/myco-runs/c1-r6 --coordinator-go \
  --resume --adopt-identity --accept-scored-cause 'refuted:step-budget'
```

The acceptance is a **narrow, recorded exception for a diagnosed cause** — not a way
past a stop. Its key is `verdict:reason`, coarser than the abort key, so accepting a
cause broadly (e.g. `refuted:persisted-mismatch`) would silence the alarm that caught
arm-003d r2's harness fault. The spend cap still bounds the damage.

It is also **recorded as starting at the resume**, not for the whole arm
(`acceptances: [{ causes, fromTrial }]`). r6's first nine rows ran with no acceptance at
all, and the ledger must not be rewritten to look as though the diagnosis had been made
when they were produced.

**Not changed, deliberately:** the planner prompt and `STEP_BUDGET`. Teaching the
agent about the dialog would break parity with Myco's arm, which is the whole point of
the comparison.
