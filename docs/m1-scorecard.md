## Reproducibility test plan (row 8)

The runbook is a *description* of the procedure. Row 8 asks whether **another coding agent**
can actually reproduce the evaluation from the repo, so the test is behavioural, not editorial.

**Protocol.** One agent who has never touched this project, given only the repo and the VM
bundle, attempts the runbook end to end, and writes down every point where the repo is
insufficient.

| Step | Pass condition |
|---|---|
| 1. Read only the repo | The operator reaches a runnable command sequence without asking a question that the repo could have answered |
| 2. Preconditions (§1) | Obtains the VM bundle, `ssh_config` + `id_ed25519`, host scripts, GUI-session permission — and **nothing else is needed** |
| 3. Reset (§3) → deploy (§4) → desktop proof (§5) | Each step's stated expected output is observed |
| 4. Generator proof (§6) | 20/20 |
| 5. Sweep (§7.3) | Produces 30 pinned rows matching the retained `params.json` |
| 6. Corrupted suite (§7.4) | Produces the ledger with zero false successes |
| 7. Evidence (§8) | `schema-validate` passes on every result and trace |
| 8. Scorecard | Regenerates `docs/m1-scorecard.md` rows **byte for byte** from the artifacts |

**Recorded, not narrated.** The operator logs: wall-clock per step, every divergence from the
runbook, and every question they had to ask. A step that "worked once I asked someone" is a
**failure** for row 8 and becomes a runbook fix.

**Known-unsatisfiable today**, stated in §10 and to be carried into the result: `build-all.sh`
is not in the repo and has never run end to end; the Windows ISO, offline payload, seed ISO and
the `clean-base` snapshots live outside the repo. Row 8 can therefore pass only in the
**"given the VM bundle"** sense, and the report must say so rather than implying a from-scratch
rebuild.

**Run when:** after the C1 arm and M1-016, using the VM bundle rather than a rebuild. Estimated
3–4 h (slot 2 in `docs/coordination/vm-queue.md`).

## Decision: arm-002 is not the baseline (2026-11-23)

**Option B.** Arm-002 completed as a **recorded run** and is **not scored** against
criterion 7. Its artifacts and analysis are kept at
`docs/research/experiments/c1-arm-002/`.

**Why.** The two arms were not told the same thing:

| | Myco's arm | arm-002 |
|---|---|---|
| Task text | "set the cell at record X, column Y, to Z, **and save the file**" | "Set the Y cell for record X to Z." — no save |
| System prompt | — | "Save and close it" (`planner.ts:78`) |

Measured consequence, re-derived from `accounting.json`: **0 `press_key` calls
across 422 actions** (`click` 398, `type_text` 24), and `modified` was 16 of 29
refutations. **Only 1 of those 16 typed the expected value** — the other 15 typed a
cell reference such as `'A24\n'`, mostly into the Name Box at `(70,146)` but not
universally (index 6 acted at `(282,277)`). All 16 terminated on
`planner-no-action` with empty `claims`, so none declared success.

So the save gap is real — no trial ever attempted Ctrl+S — but the transcript does
**not** support "typed the right value and stopped"; for 15 of 16 the right value
was never entered. The instruction difference is still the defect: the baseline was
never told to persist, while Myco's program saves as an explicit step.

**The fix, already merged into the code path.** `src/tasks/task-text.ts` renders the
canonical sentence, imports nothing, and is what `c1-trial.ts` now uses; the
rendered `instruction` is recorded on every row, so future parity is a field diff
rather than a source-reading exercise. A mutation-verified test
(`test/baseline/task-text.test.ts`) fails if the save requirement is dropped.

**Arm-003** (planned, queued after M1-016) re-runs 30 trials with the shared text,
the same Sonnet planner, the same snapshot, and a **$9.00 cap on total committed
spend**, read from `report.json.c1ChargedMicros` (**$1.632162** at arm-002's close: spike $0.076800 + arm-002 $1.555362). Design:
`docs/research/experiments/c1-arm-003-design.md`.

## Reliability row, regenerate

```bash
python3 scripts/m1-scorecard.py /tmp/m1-013/sweep-v3/trials.jsonl          # markdown
python3 scripts/m1-scorecard.py /tmp/m1-013/sweep-v3/trials.jsonl --json   # machine-readable
```

Counting rules (in the script header): the denominator is always 30, and an index without a record
is "not run". Only `verified` passes. Statuses that produced no verdict (harness, reset, deploy,
token, param, seed-mismatch) count as failures and are listed separately. The Wilson 95%
interval is over the recorded trials. The script reports the numeric threshold. To use the
count as acceptance evidence, also confirm `SWEEP_DONE`, a passing `SEED_CHECK`, and a
single pinned protocol across all 30 indices.

The pinned M1-014 checkout reproduced the v3 scorecard byte for byte from
`trials.jsonl` and independently regenerated the corrupted-suite parameter
manifest. This checks artifact replay on the host. Row 8 requires a fresh
operator to reproduce the live evaluation from the runbook.

## Open risk: guest-side fixture convert

Sweep v2 indices 1 and 3 ended `uncertain` when fixture conversion exceeded 60 seconds. A
separate cold-start probe produced its workbook at 169.4 seconds, showing that a conversion
can finish after the existing deadline. The cause of the two individual trial failures is
unconfirmed. Sweep v3 ran with the approved 240-second deadline and recorded
zero fixture conversion timeouts. See the
[conversion timeout and restart plan](research/experiments/m1-013-convert-timeout.md).
